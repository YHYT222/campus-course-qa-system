# 校园课程互助答疑系统 —— 课设辅助材料

> 本文件用于撰写课程设计报告、准备验收答辩。内容包括：ER 图文字描述、系统用例说明、双人分工清单、关键业务规则、需求对照说明与答辩口径、测试用例。

---

## 一、项目概述

本系统是一个面向高校学生的课程问答互助平台。学生按课程分类发布课业疑问，其他同学跟帖解答，逐步沉淀为课程维度的知识库；管理员负责课程分类维护、帖子内容审核、用户行为管控，并通过图表查看平台运营数据。

系统采用前后端分离架构，共两种角色：**普通学生**与**系统管理员**。

## 二、系统架构与技术选型

| 层次 | 技术 | 说明 |
|---|---|---|
| 前端 | Vue 3.4 + Vite 5 + Element Plus 2.7 + Pinia + ECharts 5.5 | 单页应用，Element Plus 提供组件，ECharts 绘制统计图 |
| 通信 | Axios + RESTful API | 前端通过 Vite 代理转发 `/api` 请求到后端 8080 |
| 后端 | Spring Boot 3.2.5 + MyBatis-Plus 3.5.5 + JDK 17 | 标准 MVC 四层结构 |
| 数据库 | MySQL 8.0 | 6 张表，utf8mb4 字符集 |
| 鉴权 | Token（内存存储）+ 拦截器 | 登录后下发 token，前端放在请求头，后端拦截器校验 |

### 后端分层说明

```
controller  接收 HTTP 请求、参数校验入口、封装统一返回 Result
    ↓
service     业务逻辑、权限校验、事务边界（接口 + Impl 实现）
    ↓
mapper      数据访问（MyBatis-Plus BaseMapper + 注解 SQL）
    ↓
entity      与数据库表一一对应的实体类
    ↓
MySQL       持久化存储
```

配套的横切模块：

- `common/`：`Result` 统一响应、`BusinessException` 业务异常、`GlobalExceptionHandler` 全局异常处理、`TokenStore` 令牌存储、`UserContext` 当前用户上下文
- `config/`：`MybatisPlusConfig` 分页插件、`WebMvcConfig` 拦截器注册与上传图片静态资源映射
- `interceptor/`：`AuthInterceptor` 登录校验 + 管理员权限校验

## 三、数据库设计（ER 图文字描述）

### 3.1 实体与属性

**用户（user）**

- 用户 ID（id，主键，自增）
- 学号（student_no，唯一）
- 用户名（username）
- 密码（password，MD5 加盐存储）
- 角色（role：0 学生 / 1 管理员）
- 头像（avatar）
- 账号状态（status：0 正常 / 1 禁言 / 2 封禁）
- 注册时间（create_time）

**课程分类（course）**

- 课程 ID（id，主键，自增）
- 课程名称（name，唯一）
- 课程简介（description）
- 创建时间（create_time）

**答疑帖子（post）**

- 帖子 ID（id，主键，自增）
- 发布用户 ID（user_id，外键关联 user.id）
- 课程分类 ID（course_id，外键关联 course.id）
- 问题标题（title）
- 问题内容（content）
- 配图地址（image）
- 点赞数（like_count）
- 审核状态（status：0 待审核 / 1 已发布 / 2 已屏蔽）
- 发布时间（create_time）

**回复评论（reply）**

- 回复 ID（id，主键，自增）
- 帖子 ID（post_id，外键关联 post.id）
- 回复用户 ID（user_id，外键关联 user.id）
- 评论内容（content）
- 回复时间（create_time）

**点赞记录（post_like）**

- 点赞 ID（id，主键，自增）
- 用户 ID（user_id）、帖子 ID（post_id），二者组合唯一
- 点赞时间（create_time）

**收藏记录（favorite）**

- 收藏 ID（id，主键，自增）
- 用户 ID（user_id）、帖子 ID（post_id），二者组合唯一
- 收藏时间（create_time）

### 3.2 实体间关系

```
用户 1 ──── N 帖子        一个用户可以发布多个帖子
课程 1 ──── N 帖子        一个课程分类下可以有多个帖子
帖子 1 ──── N 回复        一个帖子可以有多条回复
用户 1 ──── N 回复        一个用户可以回复多个帖子
用户 N ──── N 帖子        通过 post_like 建立"点赞"多对多关系
用户 N ──── N 帖子        通过 favorite 建立"收藏"多对多关系
```

一句话概括（可直接写进报告）：

> 用户与帖子是一对多关系，课程与帖子是一对多关系，帖子与回复是一对多关系；用户与帖子之间还存在"点赞"和"收藏"两种多对多关系，分别由 post_like 和 favorite 两张关联表承载，关联表上以（user_id, post_id）作为唯一键，保证同一用户对同一帖子只能点赞或收藏一次。

### 3.3 设计说明（为什么是 6 张表）

需求文档第 7 节列出 4 张核心表：用户、课程分类、答疑帖子、回复评论。

但需求 4.1.3 同时要求实现「点赞、取消点赞、收藏、取消收藏」。如果只保留 4 张表，点赞数只是一个计数字段（`post.like_count`），无法记录"谁点过"，用户重复点击就会重复加数，也无法实现"取消"；收藏更是完全没有落脚点。

因此在不改动 4 张核心表字段的前提下，**补充两张关联表**：

- `post_like`：记录点赞明细，`(user_id, post_id)` 唯一，支持取消点赞
- `favorite`：记录收藏明细，`(user_id, post_id)` 唯一，支持取消收藏

`post.like_count` 作为冗余计数字段保留，用于列表页直接展示，避免每次列表都做 count 查询。

## 六、关键业务规则说明

### 6.1 帖子审核状态流转

```
学生提交帖子
     ↓
  status = 0（待审核）  ← 此时学生端首页查不到，只有"我的提问"能看到
     ↓
管理员在后台审核
     ├── 通过 → status = 1（已发布）→ 学生端首页可见、可被搜索
     ├── 屏蔽 → status = 2（已屏蔽）→ 前台详情提示"该帖子已被屏蔽"
     └── 删除 → 物理删除，并级联删除其回复、点赞、收藏记录
```

> 实现位置：`PostServiceImpl.publish()` 写死 `STATUS_PENDING`；`PostMapper.pagePublished` 的 SQL 中固定 `WHERE p.status = 1`。

### 6.2 账号状态流转

```
正常（0） ──禁言──► 禁言（1）：可登录、可浏览，但不能发帖和回复
正常（0） ──封禁──► 封禁（2）：无法登录
任状态  ──恢复──► 正常（0）
```

### 6.3 点赞与收藏的幂等设计

同一用户对同一帖子只保留一条记录（数据库唯一键 `uk_user_post`）。点击时先查记录：

- 已存在 → 删除记录，帖子 `like_count - 1`（用 `GREATEST(..., 0)` 防止减成负数）
- 不存在 → 插入记录，`like_count + 1`

这样天然支持"取消"，也防止了刷赞。

## 七、需求对照与答辩口径

### 7.1 字段扩展说明（老师可能问）

**问：需求文档说 4 张表、字段不能改，你为什么有 6 张表、还多了字段？**

答：

> 4 张核心表的原有字段一个都没有删改。多出来的两张是 `post_like` 和 `favorite` 关联表——因为需求 4.1.3 要求点赞和收藏要能"取消"，只靠一个计数字段无法判断谁点过、也无法取消，必须记录明细。另外两个字段是为满足功能必须补充的：
>
> - `user.status`：需求 4.2.3 要求管理员能对用户"限流管理、账号管控"，没有状态字段无法实现禁言/封禁。
> - `post.title`：需求只写了"问题内容"，但帖子列表没有标题可读性很差，因此补充了标题字段并在详情页保留完整内容。
>
> 这两处属于需求描述与功能要求之间的冲突，我们选择了"优先保证功能可实现"，并在文档中明确说明。

### 7.2 技术选型说明

**问：为什么用 MyBatis-Plus 而不是原生 MyBatis？**

> MyBatis-Plus 是 MyBatis 的增强工具，底层仍是 MyBatis，保留了手写 SQL 的能力（本项目统计查询就是注解 SQL）。用它主要是省去单表 CRUD 的样板代码，把精力放在业务逻辑和权限校验上。

**问：为什么 token 存在内存里？**

> 课设环境下不引入 Redis 等中间件，用 `ConcurrentHashMap` 保存 token，重启后需要重新登录。这是有意的简化，答辩时可以说明生产环境应改用 Redis 并设置过期时间。

**问：Service 层为什么用接口 + 实现类？**

> 面向接口编程是 Spring 的常规做法，便于后续替换实现和单元测试，也符合课程要求的"标准 MVC 分层"。

## 九、可扩展方向（答辩时如有提问）

1. **最佳答案采纳**：在 `post` 表增加 `accepted_reply_id` 字段，作者可在回复中标记采纳。
2. **消息通知**：新增 `notification` 表，帖子被回复、审核结果通过时写入，前端轮询或 WebSocket 推送。
3. **全文检索**：当前为 `LIKE` 模糊查询，数据量增大后可引入 Elasticsearch 或 MySQL 全文索引。
4. **token 持久化**：将 `TokenStore` 的内存实现替换为 Redis，支持分布式部署与过期控制。
5. **敏感词过滤**：发帖与回复前接入敏感词库，作为审核机制的第一道拦截。
